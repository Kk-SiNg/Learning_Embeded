volatile and const: The Compiler Is Not Your Friend

Why the compiler will silently break your hardware code — and how two keywords stop it.

📘 Lesson 01 ⏱ ~25 min 🎯 Level 3 — Embedded C 🔗 Prereq: Basic C, MMIO concept

The Problem: Optimizing Compilers vs. Hardware Reality

You already know that peripherals on an MCU (GPIO, UART, timers) are controlled by reading and writing to special memory addresses — Memory-Mapped I/O (MMIO). To your C code, a hardware register looks like a regular variable at a fixed address.

Here's the trap. The C compiler's job is to make your code faster. One of its favorite tricks is to cache a memory value in a CPU register instead of re-reading it from RAM every time. For normal variables, this is brilliant. For hardware registers, it's catastrophic.

Consider this bare-metal polling loop on an STM32, checking if a UART has received data:

// Polling the UART status register (SIMPLIFIED)
uint32_t *uart_status = (uint32_t *)0x40011000;

while (!(*uart_status & (1 << 5))) {
    // Wait for RXNE (bit 5) to be set by hardware
}

What you expect: the loop reads the register every iteration, checking if the hardware has set bit 5.

What the compiler does at -O2: "I see you reading *uart_status in a loop, but nothing in your code changes it. I'll just read it once, cache the value, and turn this into an infinite loop. You're welcome."

⚠ This is a real production bug

This exact class of bug has caused robots to lock up mid-competition. The code works perfectly in debug mode (-O0, no optimization). The moment you build a release binary with -O2, the polling loop never exits. It's invisible in code review — the C is correct, the compiler "optimization" is the problem.

The Fix: volatile

The volatile keyword tells the compiler: "This value can change at any time for reasons you cannot see. Never cache it. Always read from and write to the actual memory address."

volatile uint32_t *uart_status = (volatile uint32_t *)0x40011000;

while (!(*uart_status & (1 << 5))) {
    // Now the compiler reads from 0x40011000 EVERY iteration.
    // No caching. The hardware can update the register between reads.
}

That single keyword changes the generated assembly from a cached loop to a genuine memory read on every iteration.

The Three Scenarios Where You Need volatile

Scenario Why Value Changes Invisibly Example
Memory-Mapped I/O Hardware peripheral updates the register UART status, GPIO input, timer count
ISR-shared variables An interrupt handler modifies the variable asynchronously A flag set in a timer ISR, checked in main()
Multi-threaded / RTOS Another task or thread writes to shared memory A shared counter between two FreeRTOS tasks
Competition tip: If you're debugging a robot and a sensor reading is "stuck" at a stale value even though the hardware is working, check for a missing volatile. It's one of the first things judges look at too.

The ISR Pattern: Where This Matters Most

In competition firmware, you constantly share data between an ISR and your main loop. Here's the classic pattern:

volatile uint8_t encoder_tick = 0;  // Shared between ISR and main

// ISR: fires on encoder edge
void EXTI0_IRQHandler(void) {
    encoder_tick = 1;
    // Clear interrupt flag (omitted for clarity)
}

// Main loop: poll for encoder event
int main(void) {
    while (1) {
        if (encoder_tick) {
            encoder_tick = 0;
            process_encoder();
        }
    }
}

Without volatile, the compiler sees that main() never sets encoder_tick to 1, so it may optimize the if branch away entirely. Your encoder processing function never runs. The robot doesn't respond to wheel rotations.

💡 What volatile does NOT do

volatile guarantees the compiler won't optimize away reads/writes. It does not make operations atomic. Reading a 32-bit value on an 8-bit MCU still takes multiple instructions, and an ISR can fire in between. For atomicity, you need interrupt masking or RTOS primitives — topics for later lessons.

Adding const: Locking Down the Pointer

Now you have a volatile pointer to a hardware register. But what if a bug in your code accidentally changes where the pointer points? Instead of reading from 0x40011000 (the UART status register), you'd be reading from some random address. On a robot, this could mean reading garbage as a "motor enable" signal.

The const qualifier prevents this. But where you place const in the declaration matters enormously:

// Declaration A: pointer is const, data is volatile
volatile uint32_t * const UART_SR = (volatile uint32_t *)0x40011000;

// Declaration B: data is const (read-only register), pointer is const
volatile const uint32_t * const CHIP_ID = (volatile const uint32_t *)0x1FFF7A10;

Reading C Declarations: The Right-to-Left Rule

C declarations read from the variable name outward (or right-to-left). Here's how to parse Declaration A:

Token Reads as
UART_SRis a …
* constconstant pointer to …
volatile uint32_ta volatile 32-bit unsigned integer

Result: "UART_SR is a constant pointer to a volatile 32-bit unsigned integer."

  • You can read and write the data at the address (it's a read-write register)
  • The compiler must access memory each time (it's volatile)
  • You cannot change where UART_SR points (the pointer is const)
✅ The idiomatic embedded register declaration

volatile uint32_t * const REG = (volatile uint32_t *)0xADDRESS;

This is the pattern used in production CMSIS headers and every professional codebase. Memorize it.

The Full Spectrum: All Combinations

Declaration Pointer Data Use Case
volatile uint32_t *p Mutable Volatile R/W Iterating over register arrays
volatile uint32_t * const p Const Volatile R/W Standard R/W register
volatile const uint32_t * const p Const Volatile RO Read-only status / chip ID
const uint32_t * const p Const Const Flash-stored lookup table
Why "volatile const" isn't a contradiction: const means your code can't write to it. volatile means something else (hardware) can change it. A status register is both: your firmware reads it, but only the peripheral updates it.

See It in Real Hardware: CMSIS Headers

Open any STM32 CMSIS header (e.g., stm32f4xx.h) and you'll see exactly this pattern in the peripheral struct definitions:

typedef struct {
  volatile uint32_t SR;    // Status register       (offset 0x00)
  volatile uint32_t DR;    // Data register          (offset 0x04)
  volatile uint32_t BRR;   // Baud rate register     (offset 0x08)
  volatile uint32_t CR1;   // Control register 1     (offset 0x0C)
  volatile uint32_t CR2;   // Control register 2     (offset 0x10)
  volatile uint32_t CR3;   // Control register 3     (offset 0x14)
  volatile uint32_t GTPR;  // Guard time/prescaler   (offset 0x18)
} USART_TypeDef;

#define USART1  ((USART_TypeDef *)0x40011000)

Every field is volatile. The #define casts the base address to a pointer to this struct. When you write USART1->CR1 |= (1 << 13);, the compiler generates a real read-modify-write to address 0x4001100C. No caching. No optimization. Exactly what the hardware expects.

Practice: Test Your Understanding

Your robot's encoder ISR sets a uint8_t flag = 1; and your main loop checks if (flag) — but the if block never executes. The code works at -O0 but fails at -O2. What's the most likely cause?

  • flag is missing the volatile qualifier
  • The ISR has a higher priority than main
  • The interrupt flag was not cleared in ISR
  • flag should be declared as const
Correct. The compiler cached the value of flag in a CPU register during main's loop. Since nothing in main visibly writes to it, the compiler assumed it couldn't change. volatile prevents this optimization.
Not quite. The optimization level (-O0 vs -O2) is the clue: the compiler is caching the variable. The ISR sets it correctly, but main never sees the update because the compiler optimized away the re-read. The fix is volatile.

What does this declaration mean?
volatile const uint32_t * const CHIP_ID = (volatile const uint32_t *)0x1FFF7A10;

  • A mutable pointer to a constant integer
  • A constant pointer to a volatile, read-only 32-bit integer
  • A volatile pointer to a constant 32-bit integer
  • A constant pointer to a normal 32-bit unsigned integer
Correct. Reading right-to-left: CHIP_ID is a const pointer (* const) to a volatile const uint32_t. The address is fixed, your code can't write to it, but the hardware might still update it — so the compiler reads from memory every time.
Remember the right-to-left rule. Start at the variable name and read outward: CHIP_ID → * const (constant pointer) → volatile const uint32_t (volatile, read-only data). The pointer can't move, your code can't write, but hardware can change the value.

In the CMSIS struct USART_TypeDef, every register field is declared volatile uint32_t. If you removed volatile, what would happen when you read USART1->SR in a polling loop?

  • It would still work because CMSIS uses __IO macros
  • A linker error at build time
  • The compiler might cache the first read, turning the poll into an infinite loop
  • The MCU would trigger a hard fault exception
Correct. Without volatile, the compiler sees no software path modifying SR and may optimize the read out of the loop. The hardware updates the register, but the CPU keeps checking its cached copy — which never changes. (Note: __IO is just a CMSIS macro that expands to volatile, so removing it and volatile has the same effect.)
No linker error or hard fault — the code compiles and runs, which is what makes this bug so insidious. The compiler optimizes the memory read away because it doesn't see any software write to SR. The polling loop never exits. This is exactly the class of bug volatile prevents.

You're writing a competition robot's motor controller. You have a volatile uint32_t *motor_speed_reg pointing to a DAC register. A teammate accidentally writes motor_speed_reg = (uint32_t *)0x00000000; somewhere. What change would have prevented this bug?

  • Making the data const
  • Using a #define macro instead
  • Declaring as volatile uint32_t * const motor_speed_reg
  • Removing volatile from the declaration
Correct. Adding const after the * makes the pointer itself immutable — the compiler would throw an error on any line that tries to reassign where it points. The data at the register address is still writable (so you can set motor speed), but the address is locked.
The bug is that the pointer was accidentally reassigned to point to address 0. Making the data const would prevent writing values, but the pointer itself would still be reassignable. A #define macro would also work but loses type safety. The best fix is * const — a constant pointer.

Key Takeaways

  1. volatile = "this value changes outside my code's control — never cache it." Use for MMIO registers, ISR-shared variables, and RTOS-shared data.
  2. const on the pointer (* const) = "this pointer always points to the same address." Use for fixed hardware register addresses.
  3. const on the data (const uint32_t *) = "my code can't write to what this points to." Use for read-only registers.
  4. The idiomatic pattern is: volatile uint32_t * const REG = (volatile uint32_t *)ADDR;
  5. volatile prevents optimization bugs, not concurrency bugs. It does not make operations atomic.
